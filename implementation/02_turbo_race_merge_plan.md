## 2. Root Cause

Three existing facts combine:

1. **`apps/{admin,storefront}/tsconfig.json`** includes `".next/types/**/*.ts"` — the standard Next.js App Router route-type include, generated by `next build`.
2. **Root `turbo.json`** declares `"typecheck": { "dependsOn": ["^build"] }`. `^build` means **upstream workspace dependencies'** build — **not** the same package's own build.
3. Consequently `typecheck` and `build` are unordered *within* a package and Turborepo runs them concurrently.

`next build` clears and regenerates `.next/types/**` at the start of its run while `tsc --noEmit` is reading files it globbed at startup → `TS6053: File … not found`.

**Why it presents as flaky:** with no `.next/`, the glob matches nothing and the race has no surface. With one present — a warm CI runner, a restored Turborepo cache, or any local build — it fires. A cold CI run passes and a warm one fails, producing an error that names a build artifact and looks unrelated to the PR under review.

## 3. Candidate Patch

Two new files. **Root `turbo.json` is not modified** — no evidence requires it, and the defect is confined to the two Next.js apps.

```jsonc
// apps/admin/turbo.json   —   identical content at apps/storefront/turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "extends": ["//"],
  "tasks": {
    "typecheck": {
      "dependsOn": ["^build", "build"]
    }
  }
}
```

## 4. Validation

Scenarios 3 and 4 above: **2/2 passes, 23/23 tasks each**, under the exact precondition that fails without the patch. The patch was then **reverted**; the working tree is clean.

### Alternatives rejected

| Alternative | Reason |
|---|---|
| Remove `.next/types/**` from `tsconfig.include` | Silently drops Next.js route type-safety. Harmless today (no routes) but a real regression once routes exist — trades a CI defect for a type-safety hole |
| Add same-package `build` to `typecheck` in **root** `turbo.json` | Slows typecheck for all ten packages, including eight that don't need it, to fix a two-package defect |
| Split CI into sequential turbo invocations | Discards the parallelism `docs/05` §4–5 chose Turborepo for |
| Accept and re-run on failure | Contradicts `docs/12` §9's flaky-test policy, which treats flakiness as a defect to fix |

## 5. Compatibility Analysis

### `docs/05` §14.1 — Task Pipeline — **COMPATIBLE**

The locked table specifies typecheck depends on "`^build` **for packages whose types are consumed across a package boundary**".

1. The requirement is **conditional and package-scoped by its own wording**, not a global uniform rule.
2. Root `turbo.json` keeps `dependsOn: ["^build"]` for all ten packages — the stated intent ("ensures `@nfi/shared` type changes are validated against every consumer before merge") is preserved exactly.
3. The patch is **additive and narrower**: same-package `build` for the two packages whose typecheck consumes their *own* build output — a case `docs/05` §14.1 does not address because it predates any Next.js app existing.
4. **`lint` is untouched** — `docs/05` §14.1's "Depends on: Nothing… fast-fails PRs without waiting on a full build" still holds.

### `docs/07` — **COMPATIBLE.** No new technology. Package Configurations are a native Turborepo 2.x feature; Turborepo `^2.3.0` is already locked (`docs/07` §20, `docs/05` §4–5). No dependency added.

### `docs/06` §9 — **COMPATIBLE.** No new top-level folder; a per-package `turbo.json` sits alongside the existing per-package `eslint.config.js` / `tsconfig.json`.

### `docs/12` §9 — **ACTIVELY SUPPORTED.** Removes a flakiness source that section requires be fixed rather than tolerated.
